## 1. 反复出现的问题

### 1.1 本地小结算与服务端不一致（问题 0007）

**现象**：问题档案 0007 记录了进度条只剩 16 格、做题范围却有 36 座宫殿；本地
`compressedIds` 69、服务端 `compressed_ids` 35。这些数字来自既有诊断记录，本次未重新读取真实学习库。

**根因**：压缩集合在三个地方各自做并集——`compressRoundPlanCards` 只加不减，
`applyServerCohorts` 取并集，`commitHydratedRoundLedger` 最终又取一次并集。
服务端有权拒绝一个仍欠重练的分组，回显里没有这些 id，但本地把它们留下了；
集合写进 localStorage，偏差跨刷新累积。

**修法**：服务端回显是唯一权威。`replaceCompressedIds` 替换而非并集；
`applyServerCohorts` / `commitHydratedRoundLedger` 采用服务端集合；只有离线、
没有服务端负载时才保留本地草稿。`compressibleRoundPlanIds` 看到源卡还有
`retryAvailableAt` 就不再请求结算，从源头避开服务端会拒绝的那一批。

**防复发**：问题档案 0007 + `roundPlan.test.ts` / `hydrateRoundLedger.test.ts`
的“被拒卡回到计划”用例。

### 1.2 两套做题窗口

**现象**：`NodeBoundQuizDialog` 与 `FreestyleScopeQuizDialog` 长期并存；同一个
“本轮评分徽标”在两处分别实现，关联题目一度完全不显示评分（问题 0002 第 11 节），
快捷键、选项打乱、题号轨道也不断只在其中一边修。

**根因**：第二个入口复制了第一套窗口，而不是复用同一份会话与展示。之后每次需求
都要求“两个窗口都改”，但门禁只检查路径字符串，无法证明行为一致。

**修法**：删除 `widgets/node-bound-quiz` 整套实现，节点角标、脑图复习卡、编辑页、
随心工具栏和轮次都进 `FreestyleScopeQuizDialog`。直接题目集由
`useDirectQuestionSetQuiz` 提供，轮次模式仍由 overlay 提供；轮次专属操作保留
位置但禁用。架构门禁改为守护这一个入口。

### 1.3 非手势滚动被当成翻页

**现象**：评分回执重排、原生吸附、迟到布局修正都会改 `scrollTop`，随后被写成
一次 `set_cursor`，页面再重排、再漂移，学习者感觉被推着走。

**根因**：把“`scrollTop` 变了”当成“学习者翻页了”。之前的修复都在 `scroll`
处理里加条件，没有一个地方回答“这次滚动有没有手指/滚轮”。

**修法**：拆出 `useFreestyleFeedScrollIntent`（只记录手指、触控笔、滚轮）、
`useFreestyleFeedScrollGeometry`（只测量页高）、`useFreestyleFeedScrollSettle`
（有手势才提交落点，没有就把已承诺的视图钉回去）。程序化滚动窗口结束后补一次
收尾，翻页落点比整页边界多 1px，避开 mandatory snap 的边界归属。
续查补齐等待/结算槽位：它没有单独的普通卡游标，不能因为 `currentIndex` 仍是最后
一张卡，就把已经打开的收尾页退回去；由 `visualIndex` 保留已承诺的收尾位置。

### 1.4 设计 token 漂移

**现象**：提交 `9fa7c4fb` 标题是“收回靛蓝”，但编辑场景顶线仍留着
`hsl(262 60% 62%)`，本次才改成 `var(--color-mark)`。

**根因**：颜色字面量散落在 CSS/TSX 中，提交只能靠人眼搜；架构门禁不检查颜色。

**现状**：残留紫尾与画布点阵已调整。2026-11-09 落地颜色数量门禁：除
`foundation.css`、路径含 `.test.` 或 `/test/` 的文件外，按文件记录 66 个文件 /
773 处存量，数量只减不增（不等于豁免所有测试辅助文件）。
新增 37 个正反例自测并接入 CI，避免扫描器失效与空基线一起假通过。
它不是完整 CSS 解析器，也拦不住等量替换；覆盖边界见
[颜色门禁](../architecture/color-literal-ratchet.md)。

### 1.5 做题卡移除后的聚合残留

**现象**：信息流不再渲染做题卡，但 `ImmersiveFreestylePage` 仍计算
`answeredQuestionIds`、`quizCount`、`resolvedQuiz`，结算页仍显示“做题卡片”指标，
溢出菜单还写着“题 0”。

**根因**：功能在卡片层移除，聚合层没有同步。信息流题卡数量已经不能代表独立
做题窗口的答题进度；不能把所有题目聚合一概解释为恒等于零。

**处理**：产品决定删掉该指标。结算页的“做题卡片”三格改为两格（已通过 / 经历过
重练）；小结算与历史记录里的“题目 N”不再显示；溢出菜单只保留导图数与候选数；
`FreestyleRoundCompletion` 不再产出 `quizCount`。历史快照里的 `quiz_count` 仍可
读取，但新快照不再写入。题目进度若将来要进结算，应做成由做题窗口写入的
`RoundQuestionProgress` 投影，而不是从信息流卡片反推。

## 5. 关联变更的统一设计

本次几组独立需求，单独看都合理，合在一起出现了共同结构：

1. **移出 / 恢复 / 排序**：三者都在改同一份队列，都需要“本地先动、服务端确认、
   迟到的旧快照不能覆盖”。现在共用 `saveQueueAction` 串行通道，三套并行 ref
   已收成 `queueEditOverlay.ts` 的一个 `QueueEditState`。状态直接复用 API 的
   `operation_id`，按 `roundId` 隔离；恢复额外记录确认版本。纯模块决定哪些意图
   仍覆盖快照，Hook 只负责收发与应用。没有另造一套操作 ID 或通用状态机框架。
2. **小结算 / 做题范围 / 进度条**：三者都读“本轮还剩什么”。现在小结算以服务端
   为准，做题范围由后端 `scope_palaces` 拥有，进度条读本地计划；0007 修的是让
   本地计划跟随服务端压缩集合。**建议**把“本轮剩余身份”做成一个后端投影
   （round → remaining card ids / palace ids），前端只渲染，不再自己合并。
3. **等级条 / 评分条 / 手动改档**：本次已经走同一条路径（目标预览 → 确认 →
   本轮已评分），没有新增第二套状态；这是正确的合并方向。

## 6. 并行冲突

- **压缩集合的双主人**：本地与服务端都认为自己在决定“哪些卡结算了”，已由
  “服务端回显唯一权威”解决。
- **排序的本地意图 vs 远端排序**：自己的排序 ACK 到来前保留最新本地意图，
  冲突重试沿用同一 `operation_id`。已补 A→B→A 回归：第一次 A 的 ACK 不能
  清掉最后一次 A。这是未提交抽离版按数组判等产生的问题，原 Hook 对象身份
  比较已有保护，不能误报成早已上线的回归。
- **恢复 vs 远端移出**：只接受最新恢复请求自己的 ACK；其版本及更旧快照仍保护，
  严格更新的移出才取代。已补恢复→移出→恢复、批量一张成功一张失败、
  已确认卡在另一张等待期间被远端移出、换轮后旧请求返回等受控 API 用例。
- **恢复与排序组合**：先应用恢复再算排序锁；修复旧 excluded 状态使刚恢复卡片
  仍留在原槽位的问题。旧轮恢复集合也不再用于新轮账本。
- **滚动有两个主人**：`useFreestyleWheelPaging` 负责滚轮翻页，原生滚动负责手势。
  滚轮路径 `preventDefault`，不再让原生吸附看到 delta；意图钩子只负责“这次
  滚动算不算用户动作”。两者职责已分开。
- **分支并行**：`.claude/worktrees/3d-11.6` 仍拥有学习小城，main 这次在沉浸页
  隐藏 `CityHorizon`。如果城市分支也改 `AppShell`，合并时会有冲突；城市改动
  继续留在该工作树，不要为了本次改动把两边合成一个提交。

## 10. 复盘后的工程约束

这次反复修改不是需要重写整个项目，而是缺少三条统一边界：

1. **状态归谁决定**：服务端拥有轮次计划，本地只拥有未确认操作及即时展示。压缩集合
   不能多处并集，操作确认不能按内容判等，跨轮请求不能共享编辑身份。
2. **视图位置不等于卡片游标**：手势可以提交翻页，布局漂移只能重钉；等待/结算页
   属于视图位置，但没有普通卡游标。必须分别测试两者，不能用一类索引替代另一类。
3. **测试必须真正经过目标路径**：旧入口消失不能静默跳过；真实点击、保存回执、
   当前 API 契约和学习日时钟共同决定证据是否有效。先修夹具，再用未放宽的业务断言
   判断产品；不能把所有红灯归为产品坏了，也不能把所有红灯归为测试旧了。

不新增通用状态机框架，不强求跨语言共用一份实现；用已有操作 ID、纯规则模块、
共享黄金样例和行为回归守住边界，比继续叠加兼容分支或复制窗口更合适。
