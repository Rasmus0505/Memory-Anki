# 本机数据库交接（实验性，默认停用）

**结论：运行时不再使用这套实现，`tools/database_handoff.py` 的所有命令（包括 `status`）在入口处直接拒绝执行。**

## 它原本想解决什么

两台设备共用同一个百度同步盘里的 SQLite 文件。同步盘会在后台分批把另一台设备的改动写进来，两个进程同时写同一份数据库并不安全。原设想是：

1. 把共享旧库整份复制到本机固定磁盘，作为该设备唯一的活动库；
2. 在旧库上留下「已冻结」标记，之后这台设备只读旧库、只写本机库；
3. 换设备时导出带校验的交接快照，另一台设备导入并获得写入权。

## 为什么停用

- 冻结靠 SQLite 的 INSERT/UPDATE/DELETE 触发器。旧版本程序或直接打开文件的客户端仍可执行 DDL、`VACUUM`、`PRAGMA`，触发器挡不住，因此不能证明单写者。
- 「离线检查」只是尝试连接本机 8012 端口，无法证明所有写入者都已停止。
- 迁移路径存在代码级错误：写入权记录需要五个字段，旧实现只传了三个；失败时旧库可能已被冻结，而本机库尚未安装。
- 快照导入会冻结所有被发现的旧库，无法证明它们属于同一份数据血统。
- 没有做过任何跨版本、真实共享目录的联调；单测只覆盖临时目录，并跳过了离线检查，因此不能作为安全证据。

## 当前行为

- `runtime_paths.resolve_database_file(app_home)` 永远返回 `app_home/学习数据/memory_palace.db`，不会因为本机存在交接标记或本机库而改道。维护工具、测试和备份都只会操作调用方指定的目录。
- 启动、Alembic 迁移、旧目录迁移、备份与恢复保持原有行为，不再被交接层包裹或拦截。
- `core/database_placement.py` 与 `tools/database_handoff.py` 只作为实验材料保留，可以被测试导入，但 `HANDOFF_WORKFLOW_ENABLED = False`，CLI 不解析参数、不创建 `device-id`、不写任何文件。
- `apps/api/tests/test_database_handoff.py` 验证的是这套隔离：CLI 对每条命令都返回 2、磁盘上不留下任何文件、数据库路径始终跟随传入的 home、启动模块不再导入 placement 层。

## 如果以后要重新启用

必须先补上这些证据，再改开关：

1. 用真实旧版本程序 + 共享同步目录做双向演练，确认旧版本写入会被拒绝而不是静默丢失；
2. 明确覆盖 DDL、`VACUUM`、`PRAGMA`、WAL checkpoint 等绕过路径；
3. 修复并覆盖「冻结后失败」的回滚路径，保证旧库不会停在半冻结状态；
4. 给导入路径加上血统校验，不能冻结非目标旧库；
5. 保留普通启动 / 迁移 / 备份路径的回归测试，确认重新启用不会影响它们。

在此之前，换设备请继续使用整份数据目录同步 + 备份/恢复，而不是交接 CLI。
