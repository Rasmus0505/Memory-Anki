## 1. 一段话说明问题

应用有四个评分按钮（忘记 / 困难 / 记得 / 轻松）。按下它们会向
**两种不同的调度算法**供给数据，取决于你处在应用的哪个部分：
英语学习卡片使用 FSRS，而宫殿复习单元——核心流程——
使用 `unit_scheduler.py` 中手写的固定阶梯。两者都用一份复制粘贴的字典
定义同样的四种评分。阶梯无法自适应：一个复习单元的下一次间隔
永远是对常量表 `(0, 1, 3, 7, 14, 30, 60, 120, 240, 365)` 的查表，
因此它永远无法学到你遗忘特定节点比平均水平更快。FSRS
可以，而且根据你的历史拟合它的优化器已经在
`requirements-optimizer.txt` 中声明。

## 2. 当前状态，实测（非估算）

2026-10-07 直接从线上数据库读取（本机的同步数据
文件夹；不是固定盘符路径）。2026-10-24 的试运行重新测得 **299** 个活跃
单元与 **1,535** 次有效评分操作，因此请把下面的数字视为
历史快照，而不是当前基线：

| 事实 | 数值 |
| --- | --- |
| 活跃复习单元 | **288** |
| 总单元数（含非活跃） | 483 |
| 曾经通过过的单元 | 185 |
| 已记录的评分操作 | **1,129** |
| 宫殿 | 124 |

活跃单元的阶段分布（即进度位于阶梯的哪一高度）：

```
stage 0 -> 127    stage 4 ->  19
stage 1 ->  11    stage 5 ->  86
stage 2 ->  30    stage 6 ->  11
stage 3 ->   3    stage 7 ->   1
```

1,129 次操作的评分分布——这就是训练信号：

```
忘记 (1) ->  13
困难 (2) -> 367
记得 (3) -> 676
轻松 (4) ->  73
```

由此可以得出两点：

- **优化器确实可用。** 1,129 次操作且四种评分都有出现，足以拟合 FSRS
  参数。这不是理论上的好处。
- **有 86 个单元处于阶段 5（30 天间隔），127 个处于阶段 0。** 猜错的
  迁移会明显重排收藏中的很大一部分，因此转换必须逐单元计算并在应用前
  审查——而不是靠翻一个开关来应用。

## 3. 为什么值得做

- **自适应。** FSRS 按每张卡片自身的历史排期到目标保持率（默认 0.9）。
  阶梯给每个阶段 5 的单元同样的 30 天，无论你是否已经遗忘过它三次。
- **一个算法，一套语义。** 如今对排期行为的修复必须在两处理解，
  重复的 `RATING_LABELS` 表明两份副本已经在结构上开始漂移。
- **更少需要维护的代码。** `unit_scheduler.py` 是 207 行排期数学加上一个
  `stage_from_legacy_interval_days` 迁移辅助函数，这些全部由 FSRS 加一个薄
  适配器替代。
- **可逆性。** `ReviewUnitRatingOperation` 已按每次评分存储
  `before_state_json` / `after_state_json`，因此转换可以从现有数据审计和
  撤销，而不需要新的台账。

## 4. 绝不能丢失的内容

这部分让变更变得不简单。`unit_scheduler.py` 编码的是**产品决策，
而非排期数学**，每一条都有注释解释它防止的真实缺陷：

| 规则 | 存在原因 |
| --- | --- |
| `MIN_PASSED_STAGE = 1` —— 通过必须落在至少 1 天之后 | 在阶段 0 记通过会让单元*今天*就到期，于是下一次队列构建又把它发出来：看起来“完成”却从未离开队列。 |
| `schedule_locked` / `schedule_changed=False` —— 在到期日之前复习会记录复习，但不推进阶梯 | 当到期集合很短时会投放填充卡片。没有这条，间隔会在零遗忘证据的情况下攀升：队列清得越勤，出现的填充越多，漂移得越快。 |
| 困难 (2) 属于重练工作，让单元保持今天到期，且每个日历日至多降一步（`ReviewUnitState.hard_penalized_on`） | 它对到期卡片和提前日期的填充必须表现一致。同一天的重练卡片上反复点困难不得持续把单元降级。 |
| 忘记 (1) 把单元降到忘记级别（阶段 0） | 最新产品决策（2026-10-21）：遗忘是重罚，不受每日一次困难规则的上限约束。这取代了早先按比例的 `LAPSE_RETENTION` 规则。 |
| 确定性抖动（`fuzz_key:stage` 的 `blake2b`） | 否则同一天的同批单元会永远一起到期。它是确定性的，因此评分*预览*与已提交的到期日绝不会不一致。 |

FSRS 提供自己的抖动和自己的遗忘处理，因此这些成为
**在 FSRS 之上刻意保留的分歧**，而不是 FSRS 会替代的东西。
尤其是 `schedule_locked` 规则是 UI 读取的产品契约
（`schedule_changed` 会呈现给用户）；它在 FSRS 中没有等价物，
必须继续有效。

## 5. 实际实现的形态（绞杀榕式，而非重写）

`unit_scheduler.rate_unit(...)` 仍是生产端口：一个返回 `UnitScheduleResult`
的纯函数，所有调用方、测试与 UI 契约保持不变。第一步实现**并不**把其内部
委托给 FSRS。它新增一个只供影子记录器使用的同级纯函数：

```
unit_scheduler.rate_unit()            <- production port, untouched
        |
        +-- product rules (MIN_PASSED_STAGE, schedule_locked, retry contract)

unit_fsrs_adapter.rate_unit_with_fsrs()   <- comparison path, no writes
        |
        +-- same product rules, applied after FSRS computes an interval
```

这是刻意比原计划少走一步。在 `rate_unit` 内部委托会在首次引入算法的
同一个提交中改变每一个真实到期日；影子台账以零排期风险提供同样的
证据。委托可以在之后经由同一个适配器发生。

适配器不导入 `modules/english` 的 `fsrs_runtime.py`。该模块
属于 English 上下文，读取英语卡片设置，允许 36500 天上限，
并启用抖动。跨上下文导入会违反依赖图；匹配那些设置
会让单元对比变得不确定。因此单元 FSRS 设置固定在适配器中
（`desired_retention=0.9`、`maximum_interval=365`、关闭抖动）。如果
FSRS 成为单元调度器，届时应把一个共享调度器工厂提取到中立模块，
而不是把 memory 耦合到 english。

### 每单元状态

`ReviewUnitState` 目前存储 `stage_index`、`has_passed`、`due_date`、
`last_passed_at`。FSRS 需要每张卡片的 stability/difficulty/due/state。影子
步骤已经把该状态持久化在 `review_unit_fsrs_shadow_states` 中，以单元 id 为键，
并针对其已消费的最后一次操作做检查点。下面的选择
仅适用于未来的生产切换。

两个选项：

- **A. 添加 FSRS 列**（`fsrs_stability`、`fsrs_difficulty`、`fsrs_state`、
  `fsrs_step`、`scheduler_version`）到 `review_unit_states`，照搬
  已经这样做的英语表（`fsrs_state`、`fsrs_step`、
  `scheduler_version="fsrs-6.3.1"`）。最干净，与既有先例一致。
- **B. 在首次评分时从 `stage_index` 推导 FSRS 状态。** schema 变更更少，
  但有损：阶段是粗粒度分桶，因此早期排期会是任意的。

**推荐 A**，因为仓库已经对英语卡片使用完全相同的列集合，
应当匹配先例，而不是再发明第三种方式。

### 迁移

1. 添加列（增量、可空——安全）。
2. 通过按 `created_at` 顺序把每个单元来自 `review_unit_rating_operations` 的真实评分
   历史经 FSRS 重放来回填。这比从 `stage_index` 播种好得多，
   因为真实历史存在。没有历史的单元（阶段 0 的 127 个，从未通过）
   直接重新开始。
3. 记录一行 `review_unit_schedule_batches`（该表已存在，用于内容对账
   降级，带 `entries_json` 与 `undone_at`），使整个转换
   可审计、可逆。
4. **先试运行并显示到期日差值**，然后再应用。有 288 个活跃
   单元时，系统性偏移（例如所有东西立即到期）必须在纸面上
   被发现，而不是在学习过程中才暴露。

### 上线

在设置开关之后发布，用真实数据对比，然后让 FSRS 成为默认，并在
对比干净之前把阶梯保留为被测试固定的回退。不要在引入适配器的
同一个变更中删除 `unit_scheduler` 的阶梯。

## 6. 风险

| 风险 | 缓解措施 |
| --- | --- |
| 288 个活跃单元的到期日发生偏移 | 逐单元重放 + 试运行差值报告 + 可逆批次行 |
| 两个调度器在迁移中途进一步分叉 | 适配器是单元*唯一*的 FSRS 路径；没有第二套集成 |
| FSRS 基于 UTC 日期时间，本模块使用 `date` | 适配器拥有边界转换，并在固定时钟上测试（仓库已有“确定性到期日”的测试文化） |
| 在转换中丢失产品规则 | §4 中的五条规则各自在适配器落地*之前*获得专门的回归测试 |
| 优化器（torch/pandas）使主安装膨胀 | 保持在 `requirements-optimizer.txt`；没有它调度器也能用默认参数工作 |

## 7. 工作量

中等，工作量主要在测试而不是适配器。大致形态：

1. 用针对*当前*阶梯的测试固定五条产品规则（前后都必须通过）。—— 小，
   且即使其余部分放弃也有价值
2. 在现有签名之后编写 FSRS 适配器。—— 小/中
3. schema 列 + 历史重放迁移 + 试运行报告。—— 中
4. 在真实数据上并排对比，然后默认切换。—— 中

## 8. 结果

证据门禁已满足：把 173 次真实评分的严格窗口经两条路径重放，
在 0 个单元上出现分歧，因此直接做了切换，而不是藏在设置之后。
与上述计划的不同之处：

- 转换没有铸造 `review_unit_schedule_batches` 行。抢救备份加上
  可重放的台账使变更可审计，标记使重跑成为无操作；批次行会让
  转换在排期历史中看起来像一次内容降级。
- 没有评分历史的单元保留其存储的到期日，且不会获得 FSRS
  检查点。适配器在这类卡片首次评分时从旧版投影播种，因此
  成熟的继承单元绝不会回退到一天间隔。
- 回滚是数据，而不是开关：回退迁移 `0077`，阶梯会从存储的
  `stage_index` / `due_date` 恢复，而切换会保持它们与真实间隔一致。
  FSRS 已记录的到期日保持原位——它们是学习者真实的排期，
  而不是缓存的估计。
