# 0004 仪表盘和学习时长超过 20 秒——打开时把全部历史账本重算了一遍

**状态**：根因已定位。用户已选定加载方式：快照 + 只补新记录。请求路径上的整本重算已拿掉；守护测试只覆盖「多一个文件不得整本重算」。现场守护（打开仪表盘必须落在客户端 20 秒预算内）还没有门禁。2026-10-11 另发现并修掉了第二条独立的卡顿来源：冷进程首次打开 209 MB 数据库（见第 6 节）。
**首次记录**：2026-10-10
**影响**：仪表盘卡片报「请求超过 20 秒未响应」；同一次打开还会拖住学习时长接口。宫殿编辑器的 409 不是这个根因，见 [0005](./0005-editor-save-conflict-and-stall.md)。

---

## 1. 用户要的体验

用户原话（2026-10-10）：

> 我希望在学习的时候拥有一个快速加载数据的体验，不要报错，不要卡顿，不要等待。

这是学习时加载的验收标准，不是建议。学习时打开仪表盘、时长、宫殿，应当直接看到数据：不弹超时卡片，不转圈干等，不把一次读取做成几十秒的重算。

用户选定的时长加载方式是「快照 + 只补新记录」。不要改回「每次打开整本重读」。保存冲突的改法另说，见 0005，未获确认前不要改保存逻辑。

## 2. 用户看到的现象

仪表盘红卡片：

> 仪表盘加载失败。网络请求失败：GET /api/v1/dashboard 浏览器错误：请求超过 20 秒未响应。

同一时段宫殿编辑器也曾同样超时：`GET /api/v1/palaces/55/editor`。连接是通的，健康检查很快，所以不是服务没起来。

## 3. 实际发生的机制

学习时长的权威数据是一串不可变 revision 文件：

```text
学习数据/time-ledger/devices/{device_id}/revisions/{revision_id}.json
```

`read_intervals()`（`apps/api/src/memory_anki/infrastructure/time_ledger_store.py`）要先把这些文件折成区间，仪表盘和 `GET /api/v1/study-sessions/time-records` 都走这里。文件大约 2700 个，放在同步盘上。没有快照时，一次打开会把历史文件整本解析一遍，实测约 45 秒，超过前端 20 秒预算（`apps/web/src/shared/api/http.ts`）。

第一次加上进程内缓存和 `_folded_cache.json` 之后，缓存热的时候仪表盘是几百毫秒。但只要目录签名和快照不一致（重启后又多了一笔新记录），请求线程仍会整本重算。这就是「修完还是超时」的原因。

现在的约定：

- 快照签名与当前 revision 目录一致：直接用快照，不重算。
- 只多了少量新文件（不超过 `_MAX_INCREMENTAL_FILES = 64`）：在快照上补这些文件，请求里返回。
- 差得太多、对不齐、或快照损坏：请求里不整本重算；先返回已有快照，整本重算放到后台，算完再换上。
- 写入、修改、删除仍追加新的 revision，不改历史文件。下一次读取只补新文件。

## 4. 证据

已证明：

- 修复前，`GET /api/v1/dashboard` 在客户端约 35 秒超时；`GET /api/v1/palaces/55/editor` 有一次 21010 毫秒才返回。`/health` 仍是几十到一百多毫秒。服务进程 CPU 几乎不涨，时间花在读盘，不是空转。
- 2026-10-10 21:08:23，同一次整本重算让多条请求一起慢：`GET /api/v1/study-sessions/time-records` 202760 毫秒，多条 `GET /api/v1/dashboard` 在 86231 到 202831 毫秒。SQL 只有几毫秒到几十毫秒，慢的不是数据库查询。
- 改成只补新记录并重启加载新代码后，实测 `GET /api/v1/dashboard` 328 毫秒，再打开 118 毫秒；`GET /api/v1/palaces/55/editor` 84 毫秒。

推断（未在这次单独计时）：2700 个小文件的耗时主要来自同步盘上的逐文件打开，不是 JSON 解析本身。所以「再优化解析」不能代替「不要在请求里整本扫」。

## 5. 已做与未做

已做：

- 请求路径不再整本重放历史 revision。
- `apps/api/tests/test_time_ledger.py` 的 `test_folded_ledger_is_cached_until_the_revision_directory_changes` 断言：快照还在时，目录里多一个文件，不得调用整本折叠。

未做，下一次不要当成已经守住：

- 没有「仪表盘必须在 20 秒内返回」的现场门禁。上面的 328 / 118 毫秒是这一台机器、这一次重启后的实测，不是持续检查。
- 后台整本重算如果和请求抢同一把进程锁，仍可能让下一次读取等待。这一点没有单独压测。

## 6. 另一条独立的卡顿来源：冷进程首次打开 209 MB 数据库（2026-10-11）

2026-10-10 22:45:53 那批 `dashboard -> 200 in 10049.76ms` 里，`sql_total_ms` 只有 92.65，而 `connect_total_ms=9042.83`——耗时不在折叠，也不在 SQL，而在**冷进程第一次打开这个 209 MB 的库**（同步盘首次触盘），量在 `apps/api/src/memory_anki/infrastructure/db/_tables/_base.py:69-91` 的 `do_connect` → `connect` 段。同秒内 `/profile/client-preferences`、`PUT /palaces/55/editor`、`/exam/overview` 也一起停在同一个栅栏上（`worker_started_ms` 都是 1–5 毫秒），因为它们都在等那一次打开。

已修：`start_db_pool_warmup()` 在启动时把 `DB_POOL_SIZE`（10）个连接一次开好，代价挪到启动，不再落在用户请求上。冷进程实测 dashboard 由 10049.76ms 降到 221.79ms，editor 由 9043.74ms 降到 27.10ms，且日志里不再出现 `DB connection initialization ... [slow]`。完整证据见 [0005](./0005-editor-save-conflict-and-stall.md) 第 6 节。

所以「仪表盘慢」有两个互相独立的成因：账本整本重算（第 1–5 节）和冷池打开（本节）。诊断时先看 `sql_total_ms` 与 `connect_total_ms` 谁占大头——前者指向折叠，后者指向连接。
