## 为什么问题容易反复

1. **同一次学习跨越多个状态所有者。** 复习排期和 encounter 由 memory 管，轮次顺序、重练 occurrence、游标和做题进度由 practice 管，前端还有临时选择和展示状态。每个部分单独合理，但编辑、重排、慢请求、连续评分同时发生时，需要用稳定身份与清晰的生效时机连接，而不是让每一层自行猜测。
2. **相似写入入口的事务与失败处理不同。** 旧事故 `docs/incidents/0003-round-stale-data-500.md:150` 明确记录过只修轮次写入、漏掉答题覆盖层写入；后来已收敛两条轮次写路径。复习会话的并发路径仍应单独验证，不应假定沿用同一种重试策略就正确。
3. **测试多为局部回归，组合场景更难覆盖。** 现有测试覆盖轮次冲突、会话身份和重练等单项行为；尚未证实有一项测试在同一轮里交错覆盖做题覆盖层写入、评分、会话创建和心跳，以及失败恢复后保持当前卡片。
4. **产品要求和历史记录缺乏明确时效标签。** 同一功能经历固定排期、FSRS 及多次定锚改动，历史文档、测试名称和兼容语义仍可能沿用旧含义；“测试通过”只说明与测试期望一致，不证明旧期望仍是最新需求。
5. **手机模拟不等于手机 PWA。** 实际操作涉及可视区域、浏览器安全区、键盘和系统控件；仅检查 CSS 字符串或打开错误页面的截图不能作为真机验收。

## 并行与关联变更

- 10 月 31 日提交同时覆盖换题、即时反馈、评分身份、错题优先、手机界面和 PWA 更新。提交整理会话明确表示部分共享文件跨功能一起提交，**个别提交不保证单独构建通过**。这已证实回滚/逐提交定位不够可靠；尚不能证明并行本身造成了当前功能冲突。
- 历史事件已经证实轮次服务和答题覆盖层曾各自提交同一轮次，而修复初期只覆盖其中一条写路径；事故文档记载该问题后来已处理。不能把已修历史冲突写成现存故障。
- 推荐统一设计：后端继续分别拥有排期和轮次，但为一次学习定义不可混淆的 round、unit、occurrence、operation 身份；更新时保留当前卡及本次展开状态；只有服务端确认后更新已完成/排期，反馈可即时但必须准确区分未保存。新增重排、错题优先或重练时都复用同一状态转换和跨模块契约。
- 手机“做题”“查看宫殿”“换题工作流”应共享弹窗可用空间与安全区验收标准，而不是分别调整固定高度；对长题干允许内容滚动，保证关闭和主要操作始终可达。

## 顶尖工程实践会额外做什么

- 把“正在看的卡片不能无故换人”“评分显示和实际保存不能矛盾”“已确认学习记录不会被重排覆盖”写成可执行不变量，而不是仅列功能清单。
- 在隔离数据库中控制两个请求的到达顺序，复现竞争；检查成功、冲突、重复请求和恢复后的最终状态。
- 用生产故障后的可验证链条：症状、实际版本、动作、请求 ID、状态变更、结果与反例；隐私优先，只记录本地必要元数据。
- 对测试和历史文档设有效期/状态：当前规范、历史事故、实验草案分开标记；清理兼容逻辑前先证明没有有效调用和迁移需求。
- 设计提交和回滚单元：功能、契约、测试尽量一起可运行；重叠文件指定责任人，合入后做组合测试，而不是根据会话标题判断独立。

## 最原始的素材

- 用户原话、截图、发生时间及当时使用入口；完整会话转录的分页记录，而不只是助手的结论。
- 实际代码和可重现的父子提交差异、工作树状态、真实接口契约、数据库模式和约束；历史日志与 request ID，注明版本和时间。
- 各测试的实际断言、测试隔离配置和原始运行结果；真实设备的视口/触控观察，以及必要时经授权使用的数据副本。不得对真实学习数据库做评分实验。
- 有时间戳的产品需求变更与验收证据；历史记录作为当时证据，不直接当成当前规范。

## 方法与工具

- 逐条对照会话分页记录、`git log` / `git show` / `git diff`，构建症状—版本—实现—测试—结果证据表。
- 追踪前端状态与 API、操作 ID、轮次版本、后端事务和数据约束；用 pytest 的隔离数据库、受控并发和失败注入复现竞争。
- 用 Vitest 检查状态转换、快速操作和延迟/失败回执；用项目规定的 hermetic Playwright fixtures 覆盖真实入口、短屏、交互与无障碍树，不连接真实 8012 数据。
- 使用 `python tools/quality_gate.py`、必要时 `--full`；启动/构建相关修改才运行有干扰性的 `--launchers`，并如实报告受环境影响的项目。
- 审核现有 recorder 的采集、脱敏、localStorage 保留、导出路径和旧记录；请求 ID 复用现有 `shared/api/http.ts`，不平行新建一套记录系统。

## 谁或什么能独立证明

- 可重复的隔离并发测试和端到端断言，证明既定状态不变量，而非只凭开发者判断。
- 一名未参与实现的审查者根据原始记录、当前代码、提交 diff 和失败反例逐条复核。
- 使用独立浏览器脚本的实际操作截图、可点击区域和无障碍树；iOS 安全区、键盘及声音仍需真实设备验证，模拟器结果不能冒充真机。
- 请求相关 ID、经过最小化和脱敏的本地诊断轨迹与服务端事务记录互相印证；缺失时明确标注无法判断。

## 修复和验证顺序

1. 隐私优先：先定义记录字段白名单与保留期限，检查现有焦点摘录/按钮文字/错误和旧历史的兼容方案，补“不含学习内容”的测试，再改采集。
2. 构造会话并发测试，验证多个 session、sequence 分配和跨轮次写入；根据结果收窄事务或数据库约束，不预设统一重试一定正确。
3. 建立跨层状态转换和组合回归：连续评分、编辑后评分、重排、错题优先、慢/失败请求、跨日、恢复与结算；确保当前状态保持和真实确认一致。
4. 移动端在真实工具栏路径覆盖长内容、短屏、安全区、虚拟键盘和关闭按钮；区分脚本/模拟/真实设备证据。
5. 逐项确认旧重练状态、文档和测试是否仍有调用或历史价值，再有边界地删除或标记，不进行大范围盲清理。
