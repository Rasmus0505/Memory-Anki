## 0. 一页结论

1. **最核心的问题不是功能少，而是“状态不一致”。** 同一个事实在多处各存一份：仪表盘缓存、随心轮次账本、评分保存队列、学习日边界、配置清洗器。只要其中一处没有失效或版本号，页面就会显示旧数字、白屏，或者“设置了却没生效”。
2. **底层架构不需要推倒重来。** 模块化单体、公开 facade、依赖方向检查、14 个前端模块、380 个后端源文件的 mypy 全量检查，这些基础是好的。问题集中在“最后一公里”的契约与失效协议，而不是分层本身。
3. **这一周最典型的两个例子：**
   - 仪表盘在 2026-10-11 的提交 `82f7f8af`（提交信息只有一个“1”）里引入了快照缓存；冷启动时接口返回只有 `{"snapshot": {"status": "pending"}}`，前端立刻读 `today_new_palaces`，于是白屏。这个缓存还把 `time.monotonic()` 写进磁盘快照，进程重启后旧快照会被当成“刚生成”。本次已改成“5 秒合并读 + 写请求失效 + 只存内存 + 永不返回半成品”。
   - 随心配置里有一个可见的“题型”下拉框（7 个选项），后端 `overlay_quiz.py` 却明确 `del question_type`。用户选了也不会生效。本次已删掉这个无效控件；后端字段的彻底清理列入下一阶段。
4. **FSRS 值得做，但不能直接切换。** 用真实 299 个活跃单元、1,535 条有效评分回放：不设考试边界时，90 天复习量从 1,068 降到 661（−38%）；叠加当前 2026-12-20 考试与冲刺模式后，到考前一天的总量从 1,200 降到 815（−32%），考前最后 7 天峰值从 60 降到 37。建议先写适配器、影子对比、分批切换，目标保持率先用 0.90。**2026-10-24 已落地第一步：FSRS 适配器 + 实时影子记录，生产排期没有改变；见 [2026-10-24-FSRS影子适配基线.md](./2026-10-24-FSRS影子适配基线.md)。**
5. **测试不是“附属品”，它本身就是这次复盘的主证据。** 仪表盘相关后端测试从 10 月 11 日起就是红的；一周的 E2E 里有 21 个失败，其中大部分是“产品已经改了、测试还在断言旧行为”。本次已修掉这些过期测试，并把“全绿”重新变成可执行的验收线。

## 1. 复盘范围、方法与边界

### 1.1 范围

- 最近一周（2026-10-17 至 2026-10-24）的 27 个提交。
- 2026-10-01 以来的 186 个提交，用于看“反复修改”的长周期模式。
- 最近一周的全部对话记录（含并行会话），用于还原“为什么改了又改”。
- 当前工作树中的代码、测试、架构文档、运行脚本。
- 本机同步数据目录中的真实 SQLite 数据库（只读打开），用于验证排期与负载。

### 1.2 方法

1. **从症状倒推提交**：对每个反复出现的问题，用 `git log -S`、`git show --stat` 找到引入点，而不是从最新代码猜。
2. **找状态的所有者**：同一事实存在几份？谁是源？什么时候失效？失败时页面看到什么？
3. **用真实数据复现**：排期问题用 `review_unit_rating_operations` 回放；负载问题用 90 天投影和考试边界投影。
4. **先修低风险、可验证的**：补测试、删无效控件、修时区、修缓存；高风险改造（FSRS）只做只读对比，不直接改库。
5. **把“全绿”变成验收线**：标准门禁 8/8、架构测试 171 项、目标 E2E 25 项通过。

### 1.3 边界与未验证项

- 没有生产环境遥测；所有“用户会怎样”都是基于真实数据的模拟，不是线上埋点。
- FSRS 回放的阶段一致率 247/299，到期日一致率 165/299；差异来自历史手动改期和回放未覆盖的“当天再次出现”规则，所以“切换后会怎样”以库中当前状态为准。
- 没有模拟考后恢复、当天重试、提前复习的真实组合；这些会改变绝对数字，但不改变“FSRS 总量更低、最后一周峰值更低”的方向。
- 没有在两台设备上做同步冲突实测；并行冲突的分析基于 git 历史与会话记录。

#### 四个根因

1. **派生状态没有失效协议。** 缓存、轮次账本、评分 outbox、自动保存都是“从源数据算出来的第二份状态”。只要没有版本号/失效信号，就一定会出现“源变了、派生没变”。
2. **同一语义有多份定义。** 两个调度器、两套配置清洗、两套评分标签、前后端各一份字段列表。每多一份，就多一个漂移点。
3. **边界没有运行时契约。** 后端可以返回半成品；前端默认字段一定存在；配置字段可以被接受但被丢弃；导入可以写半批。类型检查管不到这些。
4. **质量门禁的红线不清晰。** “预存失败”“先跳过”“本地为准”一旦成为习惯，回归就会被当成噪音。测试过期不是测试的问题，是产品变更没有带着测试一起走。

### 2.2 架构评估：需不需要重构？

**结论：不需要推倒重来，需要一次“契约与失效”专项整改。**

#### 做得好的部分

- 模块化单体符合这个产品：两台 Windows、本地 SQLite、PWA 与桌面共用后端；没有引入公网 SaaS 或多用户复杂度。
- 依赖方向有机器可执行的守卫：`tools/check_architecture.py`、`context-map.yaml`、import-linter 3 条契约、前端 ESLint boundaries。
- 公开 facade 纪律存在：跨模块走 `public.ts` / `api.py`，不是随便 import 内部。
- 类型边界较完整：后端 380 个源文件 mypy 全量通过；前端 `tsc -b --noEmit` 通过。
- 反馈系统统一走 `cue()`，有 owner 作用域，符合 AGENTS.md 的约束。

#### 主要缺陷与处理顺序

| 优先级 | 缺陷 | 影响 | 建议 |
| ---: | --- | --- | --- |
| P0 | 派生状态无失效协议（仪表盘、轮次、评分、自动保存） | 白屏、旧数字、跨天复活、保存状态错乱 | 每个派生状态明确 owner、版本、失效触发；先补回归测试 |
| P0 | 配置字段“接受了但不用” | 用户以为设置了，实际没生效 | 建“支持字段”清单；未消费字段从 schema 删除或显式 deprecated |
| P1 | 双调度器（英语 FSRS / 宫殿固定阶梯） | 两套语义、两套测试、修一次要改两处 | 用适配器把 `rate_unit` 内部换成 FSRS；保留五条产品规则；影子对比后分批切换 |
| P1 | 运行时 schema 校验不足 | 后端改字段，前端白屏/掉块 | 前端 API 边界统一 decoder；后端响应模型补齐；契约测试 |
| P1 | 内容导入无完整性门槛 | 半批入库、字段错位、题目答案错位 | 导入前验证 schema/计数/抽样；失败整批拒绝；保留来源与校验和 |
| P2 | 仪表盘缓存仍在 presentation | 未来多入口会绕过失效 | 迁到 application 读模型；presentation 只做 HTTP |
| P2 | SQLite 单写者 + 长请求构建 | 写锁竞争、首屏等待 | 控制事务长度；重活移出请求；WAL 下避免长读事务 |
| P2 | 超大文件 | 修改风险高、冲突多 | 三个随心文件已登记临时例外；下一次随心重构必须拆 |
| P3 | 测试脆弱（日期、精确字符串、旧 UX） | 门禁红、误判为产品坏 | 固定时钟、意图断言、行为变更同提交改测试 |

#### 架构判断

- **不要**为了“更现代”拆微服务、加消息队列、上云。这个产品的数据一致性靠单写者 + 本地事务，拆开只会增加分布式状态。
- **要**把“状态一致性”当成一等架构能力：谁拥有、何时失效、失败时展示什么。这比再加一个页面更重要。
- **要**把“产品规则”从实现细节里提出来：`MIN_PASSED_STAGE`、提前复习锁定、困难同日只降一次、忘记归零、确定性 fuzz，这些是产品合同，不是调度数学。

**判断标准：** 一个字段/分支如果“用户能看见、后端不消费”，就是缺陷，不是兼容；一个兼容如果“没有删除计划”，就是永久债务。

### 2.5 多个独立变更组合后的优化空间

这一节是本次复盘最重要的“组合视角”。很多需求单独做都合理，放在一起才出问题。

| 组合 | 单独看合理 | 组合后的冲突 | 统一设计 |
| --- | --- | --- | --- |
| 仪表盘快照缓存 + 复习写操作 + 两台设备同步 | 缓存让首屏快 | 写后不失效 → 旧数字；磁盘快照跨重启 → 更旧的数字 | 读模型只做 5 秒合并；写请求统一失效；不跨进程持久化；外部同步后首次读强制重建 |
| FSRS + 考试冲刺模式 | FSRS 让间隔自适应；冲刺模式防止排到考后 | FSRS 的长间隔会被冲刺模式拉回最后一周，可能形成新的堆积 | 适配器里把 `SprintHorizon` 作为一等规则；影子对比必须同时看“总量”和“最后 7 天峰值” |
| 学习日 3 点翻页 + 周统计 + 到期日 | 各自都对 | 本地墙钟、UTC-naive、学习日三套时间混用，周统计差 8 小时 | 单一时间入口；所有“今天/本周”走 `local_day`/`study_day_of`；禁止 `datetime.now()` |
| 题型下拉框 + 后端 overlay 配置 | 前端给用户更多控制 | 后端明确丢弃 → 用户白选 | 先删 UI；再删字段；需要题型筛选就真正实现 |
| 随心轮次计划 + 评分 outbox + 手机布局 | 轮次计划让排队可控；outbox 让保存不阻塞；手机布局要紧凑 | 三者都改同一批文件，测试断言互相打架；大文件冲突 | 按 owner 拆文件：轮次计划 / 评分状态 / 布局；事件契约固定；E2E 只断言用户可见行为 |
| PWA + 桌面启动器 + 前端构建 | 共用前端和后端，部署简单 | 后端进程陈旧、前端 bundle 陈旧，页面白屏但源码是对的 | build/version 握手；启动器健康检查；前端发现版本不一致提示重载 |
| 题库导入 + 脑图绑定 + 复习单元 | 各自有流水线 | 导入字段错位会一路传到绑定和复习；没有完整性门槛 | 导入前验证；绑定前核对；复习前不修复文档（读投影不写） |
| 并行会话 + 共享工作树 | 并行提高速度 | 同一文件多写者、catch-all 提交、合并“以本地为准” | 文件所有权；一个任务一个分支/会话；提交按主题拆；合并必须看 diff |

**统一原则：** 组合变更时，先问“这些变更共同改变了哪一个状态？”如果答案超过一个，就先画状态所有权图，再写代码。

### 2.6 并行开发冲突：哪些冲突没有真正解决

#### 证据

- 最近一周 27 个提交，其中至少 3 个合并提交直接写“冲突以本地代码为准”或“保留本地完整工作树”：
  - `f22e15bf`（2026-10-03）`merge: 并入远端 main，冲突以本地代码为准`
  - `05199f3b`（2026-10-06）`merge: 并入 main 的随心进度同步与进度轨，保留轮次回执、时长账本和存储锁`
  - `8d6b9068`（2026-10-07）`merge(web): 并入随心工作区常驻与其热路径优化`
- 同一个提示词在同一秒启动了两个会话（`98190d9c` 与 `5c999ad6`），说明并行不是“分工”，而是“重复”。
- 出现过多主题混合的 catch-all 提交：
  - `6171cd03`（10-21，提交信息“1”）48 个文件，夹带 `memory_anki_juicy_edition.html` 删除和 `palace-mindmap-optimization.html` 新增；
  - `8b2838a7`（10-22，“番茄钟之前”）22 个文件，实际是脑图/翻卡/手机布局混合；
  - `a23e8e40`（10-23，英语听写）59 个文件，+12,016/−4,550。
- 同一周内 `practice` 的队列、配置、轮次文件被多个提交反复触碰，测试与实现不同步，最终表现为 21 个 E2E 失败。

#### 后果

1. **无法审计“远端改了什么”。** “以本地为准”合并后，结果与远端父提交的 diff 只能说明“本地多了什么”，不能证明“远端少了什么”。
2. **重复实现。** 两个会话做同一件事，最后只能留一份，另一份的时间与上下文浪费。
3. **测试债。** 行为改了，测试没跟着改；下一次会话看到红测试，以为是预存问题，继续叠加。
4. **提交不可回滚。** catch-all 提交里混着无关文件，想回滚一个功能会带上别的改动。

#### 建议的协作规则

- **一个文件同一时间只有一个写者。** 开工前在任务里写明“我拥有这些文件”；别人要改，先发消息。
- **一个任务一个分支/会话。** 不再用“同一秒开两个同提示词会话”的方式并行。
- **提交按主题拆。** 迁移、重构、UI、测试分开；禁止“1”“小优化”“睡前”这类提交信息。
- **合并冲突必须看 diff。** 不允许 `--ours`/“以本地为准”作为默认策略；冲突解决要写“保留了什么、丢弃了什么、为什么”。
- **每次会话结束留一份 digest。** 记录改了哪些文件、哪些测试、哪些未完成；下次会话先读 digest，再读代码。
- **共享工作树不做 `git stash`/`reset --hard`。** 本次复盘遵守了这一点；后续也应如此。

## 3. 四个元问题

### 3.1 这个领域的顶尖专家会做哪些“用户没要求”的事？

1. **画状态所有权图，而不是先写页面。** 每个事实只允许一个 owner；缓存、账本、outbox 都标“何时失效、失败展示什么”。
2. **给产品规则写合同测试。** 例如“通过至少排到次日”“提前复习不推进”“困难同日只降一次”“忘记归零”“fuzz 确定性”。这些规则比调度算法更容易被改坏。
3. **建立影子模式。** 新算法不直接改用户数据，先并排算两份排期，比较差异，再分批切换。
4. **在导入边界做完整性门槛。** schema、计数、抽样、来源、校验和；失败整批拒绝。
5. **做运行版本握手。** 前端 bundle、后端进程、数据库迁移版本三者不一致时，主动提示，而不是白屏。
6. **把测试当产品表面。** 红就是红，不允许“预存失败”长期存在；行为变更必须同提交改测试。
7. **做负载与保留率的度量。** 不只看“功能有没有”，还看“每天多少张、最后一周多少张、考前是否堆爆”。
8. **写 ADR/决策记录。** 为什么 `MIN_PASSED_STAGE=1`、为什么冲刺模式只拉回不延长、为什么 fuzz 必须确定性。
9. **做属性测试。** 对日期、跨天、时区、重复评分、乱序响应做生成式测试，而不是只写手写用例。
10. **保留回退路径。** 新调度、新缓存、新导入都能一键回退，且回退不依赖“记得改回来”。

### 3.2 他们会从哪些“最原始的素材”入手，而不是已经整理好的素材？

- **原始题库 JSON/PDF/字幕**，而不是导入后的清洗结果；字段错位只有在源文件才能看出来。
- **原始 git 历史**（`log -S`、`show --stat`、merge parents），而不是提交信息；提交信息“1”什么也说明不了。
- **原始会话记录**，包括并行会话和失败尝试；重复劳动的证据在那里。
- **真实浏览器里的 E2E trace/screenshot**，而不是单元测试的通过率；白屏和布局问题只在真实渲染里出现。

## 4. 修改后的题目（把“改题目”升级为可验收的整改任务）

原始题目是“修改我的题目”。更准确的任务应该是：

> **不要只改题目或补功能。** 以真实数据和运行中的产品为证据，找出反复出现问题的状态一致性根因；在不破坏现有产品规则的前提下，建立失效协议、契约校验、单一调度与导入完整性门槛；给出一份可验证、可回滚、按优先级执行的整改计划，并先完成低风险修复与回归测试。

拆成四条工作流：

### 工作流 A：状态一致性（P0）

- 仪表盘：5 秒合并、写失效、只存内存、永不返回半成品（本次已完成）。
- 随心轮次：跨天强制对账；账本带日期版本；客户端候选不能替代后端到期集合。
- 评分 outbox：一个卡片一个串行 lane；最新意图可见，但网络请求串行；失败显示“未保存”，不冒充已保存。
- 时间：所有“今天/本周”走 `local_day`/`study_day_of`；禁止 `datetime.now()`。

**验收：** 冷启动不白屏；写后读不旧；跨天不复活；保存失败不显示已选；周统计不再差 8 小时。

### 工作流 B：契约与配置（P0/P1）

- 建“支持字段”清单：每个前端可见配置必须被后端消费。
- 删除或标记 deprecated：`question_type`、`weak_priority`、`mastery_buckets`、`overlay_question_range`、`new_placement`、`review_new_ratio`、`due_policy`。
- 前端 API 边界统一 decoder；后端响应模型补齐。
- 导入前 schema/计数/抽样验证；失败整批拒绝。

**验收：** 用户能选的都生效；后端改字段不会白屏；导入不会半批入库。

### 工作流 C：调度统一（P1，考前不做全量切换）

- 保持 `rate_unit(...)` 签名，内部适配 FSRS。
- 五条产品规则先写回归测试：通过至少次日、提前复习锁定、困难同日只降一次、忘记归零、确定性 fuzz。
- 加 FSRS 状态列，按真实历史回放；写可撤销批次。
- 影子对比：阶梯 vs FSRS，按单元列差异；先看 57 天考试窗口和最后 7 天峰值。
- 目标保持率从 0.90 开始；保留 0.95 作为考前可调项。
- 分批切换，阶梯保留一个版本周期。

**验收：** 五条规则测试在切换前后都绿；影子报告显示总量与峰值；可一键回退。

### 工作流 D：工程流程（P1）

- 门禁全绿才交付；禁止“预存失败”长期存在。
- 行为变更同提交改测试；禁止只改实现不改断言。
- 一个文件一个写者；一个任务一个分支/会话；提交按主题拆。
- 合并冲突必须写“保留/丢弃/为什么”，禁止默认“以本地为准”。
- 增加 build/version 握手和启动器健康检查。

**验收：** 门禁绿；E2E 稳定；合并可审计；PWA 不再因陈旧进程白屏。
