## 修复：PWA 脑图 ⋯ 菜单左侧被裁 + 桌面端弹窗偏下/底部越界

两处根因与改法（均只动前端）：
1. `apps/web/src/modules/content/ui/mindmap-editor/MindMapPageToolbar.tsx`

   内容/字体后续变大时在用户未手动拖动（`autoCenterLockedRef`）前持续重新居中，
   collapsed 胶囊态不启用、首次回调跳过以免展开时跳动。

## 06:19 大面积 500 + 手机端 session POST 15s 超时（根因：SQLAlchemy 连接池耗尽）

用户报告：`POST /api/v1/review/units/572cfa71a96040bd9339af765478d02d/sessions`
浏览器侧 15s 超时（`SESSION_START_TIMEOUT_MS`），但服务端在线。

**日志铁证**（`logs/pwa-api.log` 第 1190 行起为本进程，06:14:37 启动）：
- 7913 行：该请求服务端 **06:19:40.127 才返回 200，耗时 34275ms**。前端 15s 早就断了，
  服务端仍在跑并写成功 → 客户端与服务端状态分歧（预期的 mutation 语义被打破）。
- 46 处 `sqlalchemy.exc.TimeoutError: QueuePool limit of size 5 overflow 2 reached,
  connection timed out, timeout 30.00`。
- 23 个 500，全部是 `in 30xxx ms`——正好撞上连接池 checkout 的 30s 默认超时。
  涉及 `/review/units/*/sessions`、`/palaces/41|17|40/quiz-node-bindings`、
  `/freestyle/rounds/476124df.../actions`。

**因果链**：
1. 06:18:45 手机从 `/freestyle` 切到 `/freestyle-2`（另一个 workspace 的 feed）。
   页面并发拉起 review queue / 多个 palace projection / ladder-progress /
   quiz-node-bindings / dashboard / grouped-summary。
2. 06:18:45–06:19:02 大量请求已处于秒级（`palaces/grouped` 2066ms、
   `ladder-progress` 4295ms、`freestyle/rounds/actions` 1636ms），
   同时 FreestyleUnitReviewCardView 快速轮播不断 POST `/review/units/{id}/sessions`。
3. 06:19:04 后**服务端整体停摆约 9 秒**：连 `/session/live/commands`（正常 4-10ms）也
   在 06:19:13 批量返回 8520/7857/7532...ms。此时池中 7 条连接全部被占满。
4. 06:19:33 起，排队等连接的请求在 30s 后集中抛 TimeoutError → 23 个 500。
5. 幸存请求（含用户这条）在 34s 后才拿到连接并 200。

**根因判定**：`infrastructure/db/_tables/_base.py` 的
`pool_size=5, max_overflow=2`（7 条上限）对"一次 feed 打开"的并发量严重不足；
且默认 `pool_timeout=30` 与前端 15s 传输预算方向相反（内层比外层慢一倍）。

**分层预算被打破**：MEMORY.md 记录的「内层先失败」不变量，
本应 `SQLITE_LOCK_WAIT_SECONDS=10` < `SESSION_START_TIMEOUT_MS=15s` <
`GET_REQUEST_TIMEOUT_MS=20s` < `SESSION_LOAD_TIMEOUT_MS=30s`。
但**池 checkout 超时没纳入这条链**，SQLAlchemy 默认 30s 直接顶穿全部四层。

**待办（尚未改代码）**：
- 给 engine 显式设 `pool_timeout`，必须 < `SESSION_START_TIMEOUT_MS`(15s)，
  建议 3-5s，让池枯竭以 503/可重试错误快速暴露而不是挂 30s。
- 扩大 `pool_size`/`max_overflow`（或改用 `QueuePool` 之外的策略）以匹配 feed 打开时的并发峰值。
- 评估 `/freestyle-2` 首屏是否重复请求了 projection/queue/bindings（同一数据被多个组件各拉一次）。
- 评估 ReviewUnitState 相关查询是否持有连接做慢投影（`_definitions_for_palace` 走缓存，
  但 `reconcile_palace_units` 会写；写事务持锁时其他连接只能等）。
- `pool_pre_ping=False` 在 USB/网络盘上有风险，但本次非主因。
